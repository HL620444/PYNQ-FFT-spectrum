# 工程技能包提炼 (Skill Package)

本项目在研发过程中，经历了从传统纯硬件方案向异构软硬件协同方案的架构转变。以下是我们从实际板级调试、时序违例、数据溢出等痛点中提炼出的 5 项核心工程技能与踩坑复盘。

---

## 技能一：AXI-Stream 长流水线物理时序死锁的抗干扰设计

*   **失败现象**：初期采用纯硬件 DDS+FFT 方案时，在 100MHz 主频下，系统跑板级实测输出全是 0、65530 或 4294967292 等垃圾数据。
*   **排查过程**：通过 Vivado 的 `Report Timing Summary` 定位，发现跨模块的 `TREADY` 握手信号存在漫长的组合逻辑路径，导致建立时间（Setup Time）出现严重的负裕量（Negative WNS），上下游模块互相等待，发生物理死锁。
*   **技能提炼与解决方案**：
    1. 摒弃直接握手，在 DMA 与 FFT、FFT 与后级模块之间，**插入 AXI4-Stream Data FIFO（深度 1024）作为缓冲“水库”**。
    2. FIFO 彻底切断了上下游的长路径，实现了物理隔离，重新给 `TREADY` 信号打拍。
*   **验证与边界确定**：修改后，时序报告 Failing Endpoints 降为 0。实测证明：在 100MHz 及以上的长流水线设计中，跨越 3 个以上核心 IP 的握手信号，**绝不能依赖 EDA 工具的自动布局布线，必须人工插 FIFO 或加 Pipeline 寄存器**。

---

## 技能二：基于泰勒级数展开的硬件实时加窗算法

*   **观察与痛点**：传统 FPGA 加窗依赖 ROM 查表，消耗大量 BRAM 资源，且加载 `.coe` 文件繁琐。如果我们做纯软件定义无线电（SDR），每次改频率都去改 ROM 是不现实的。
*   **技能提炼与解决方案**：
    1. 放弃查表，利用泰勒级数展开近似计算余弦值：\(\cos(x) \approx 1 - \frac{x^2}{2!} + \frac{x^4}{4!}\)。
    2. 使用 Q15 定点化（乘以 32768）和算术右移（`>>>`）在 Verilog 中实现浮点运算。
    3. 采用多级流水线打拍（`x_d1`, `x2_d2`, `x4_d3`），避免长组合逻辑导致时序违例。
*   **验证与边界确定**：RTL 仿真中，输入恒定 4096 的直流数据，边缘系数成功衰减至 328，证明了硬件加窗逻辑正确。边界在于：**泰勒级数截断到 4 次方时，对于 \(2\pi\) 范围的精度衰减在 Q15 精度下可接受，完全满足汉明窗需求**。

---

## 技能三：硬件级总线带宽压缩与峰值检测状态机设计

*   **观察与痛点**：若将 8192 点 FFT 的复数结果全部回传给 PS 端，需要占用 32KB（8192×4字节）的 DMA 带宽，不仅延迟高，且 PS 端软件遍历寻峰耗时极长。
*   **技能提炼与解决方案**：
    1. 在 PL 端自研 `peak_detect.v` 模块，设计状态机（IDLE, RECV, SEND, DONE）。
    2. 在 RECV 状态遍历 8192 个频点，实时比较复数模平方 \((I^2 + Q^2)\)。
    3. 当 TLAST 拉高时，状态机切换至 SEND 状态，仅将**峰值索引和峰值幅值**（共 8 字节）传给 DMA。
*   **验证与边界确定**：仿真显示，接收完毕瞬间即可输出峰值索引（仅延迟 1 个流水线周期）。**总线数据量压缩了 4000 倍**。边界确定：模平方比较仅适用于寻找单频主峰（如 10MHz），若需分析多载波，此模块需升级为多峰值缓存机制。

---

## 技能四：16 位有符号补码运算与位宽截断保护

*   **失败现象**：硬件乘法器计算模平方 \((I^2 + Q^2)\) 时，峰值检测频繁找错索引，甚至负数算出的结果比正数还大。
*   **排查过程**：定位为 Verilog 默认将输入当成了无符号数（Unsigned）处理。16 位补码的负数最高位是 1，被当成了极大的正权值参与乘法。
*   **技能提炼与解决方案**：
    1. 在模块声明时强制使用 `signed` 关键字：`input signed [15:0] i_val` 和 `output signed [31:0] ...`。
    2. 乘法结果长达 32 位，在输出截断时，不能简单取 `[15:0]`，必须取高位 `[30:15]` 以保证不丢失有效数值。
*   **边界确定**：只要有负数参与乘法，无论数据多小，必须严格声明 `signed`。计算完成后需及时打拍，防止 DSP48 资源组合逻辑过长导致 100MHz 下时序崩塌。

---

## 技能五：PYNQ 软硬件协同的“防驱动死锁”技巧

*   **观察与痛点**：在 Jupyter 中连续多次运行 Python 脚本控制 DMA 时，由于上一次传输未正常释放，会导致 `dma.sendchannel.transfer` 卡死，或报错 `DMA is not started`。
*   **技能提炼与解决方案**：
    1. 每次在 Python 端启动 DMA 传输前，**强制复位并重启通道**：
       `dma.recvchannel.stop(); dma.recvchannel.start()`
       `dma.sendchannel.stop(); dma.sendchannel.start()`
    2. 分配缓冲区必须使用 `pynq.allocate`，确保物理地址连续。
*   **验证与边界确定**：通过引入 `stop()` 再 `start()` 的逻辑，多次循环点击 Jupyter 的 Run 按钮，系统依然能稳定输出 `9.998 MHz`。边界：在 S2MM 接收不到数据时，必须检查 PS 端分配的 `output_buffer` 大小是否与 PL 端状态机发出的字节数完全匹配。

---

## 总结
通过上述 5 个核心技能点的打磨，我们不仅成功绕过了 100MHz 下的时序死锁，还将系统的端到端延迟压榨到了 1.776ms。这些技能包不仅对本次竞赛，对后续基于 Zynq 的高速数据采集与处理系统开发，都具有极高的参考复用价值。
